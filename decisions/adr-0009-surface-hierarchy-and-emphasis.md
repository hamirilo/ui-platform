# ADR-0009: 面の階層と強調の予算 — カードは「もの」の単位、まとまりは見出しと余白で作る

**ステータス**: 採用

**関連**: [ADR-0007](adr-0007-template-class-contract-and-presentation-islands.md)（React部品とテンプレート用クラスを1:1にする。このADRで足す部品にも適用する）

## コンテキスト

利用側Applicationの画面がカードだらけになり、どれが重要な情報か読み取れないという指摘があった。
例として、周知リンクの解析画面（dx-portal）は1画面に枠つきの面が11個並ぶ。

- 指標4つ（総クリック・ユニーク・開封・除外）が同じ大きさの箱で並び、主指標のユニークは薄い色の枠でしか区別されない。値が0の参考値も主指標と同じ重さで見える。
- 「チャネル別」「参照元」「配布用URL」の各節が、すべて枠で囲まれている。見出しより枠のほうが強く、画面の構造を枠線が作っている。
- 環境別のブラウザ・OS・デバイスは同じ64クリックを3つの切り口で見たものなのに、カード3枚に分かれている。
- 参照元は1行・100%なのに、表の箱をまるごと使っている。
- 注記が箱の外に置かれ、どの箱の話か読み手が対応づけている。

個々のApplicationの問題に見えるが、このrepositoryにも原因がある。

1. **禁止だけがあり、代わりの手段がない。** [DESIGN.md](../DESIGN.md) と [design-system/README.md](../design-system/README.md) は「過剰なカード分割をしない」と書くが、何が過剰かの基準も、カードを使わずにまとまりを作る部品も無い。まとめる道具がCardしかないので、人もAI agentもCardを選ぶ。
2. **部品がそれぞれ自分で面を描く。** Table（`.cn-table-container`）、Stat（`.cn-stat`）、`.filter-bar`、Accordion / `.disclosure` が、それぞれ枠・角丸・`bg-card` を持つ。Storybook「テンプレート/標準アプリ」はCardを1枚も使わずに、Stat 4枠 + 絞り込み枠 + 表枠の6つの箱が並ぶ。ここへApplicationがCardを重ねると、面の中に面ができる。
3. **見本がカードの使い方を教えている。** 「テンプレート/詳細画面」は「本文のDescriptionListをCardで区切る」を推奨構成にしている。[screen-layouts.md](../design-system/screen-layouts.md) は「Grid / Card 構成」をアプリが自由に変えてよい項目に入れている。
4. **強調の手段が決まっていない。** 何を大きく・目立たせるかの決まりが無いため、全部を同じ箱に入れ、主役は枠の色で示すことになる。

問題はCardの見た目ではなく、**画面のどこに面を置いてよいか**と**何をどれだけ強調するか**が決まっていないことにある。

## 決定

### 1. 面の階層を3段に決める

| 段 | 使うもの | 使ってよい場面 |
|---|---|---|
| 地（ページの背景） | 見出し + 余白（必要なら区切り線） | **まとまりを作るときの既定。** 詳細画面の各節、集計の各節、設定項目の群 |
| 作業面 | 枠つきの面を1つ | 1つの作業領域に境界が必要なとき。横スクロールする表、入力フォーム本体、絞り込み + 一覧の組 |
| カード | Card | **そのまとまり自体が1つの「もの」**のときだけ |

カードにしてよいかは次で判断する。

- 同じ形のものが複数並び、**1つずつ** 開く・選ぶ・操作する・並べ替える対象になる（一覧の各項目、選択肢、独立したウィジェット）。
- 名前を付けて、画面から単独で取り出しても意味が通る。

どちらも当てはまらなければ、カードではなく地の上の節にする。
**同じ集計を切り口ごとに分けたもの、詳細画面の項目群、1つしかないまとまりはカードにしない。**

### 2. 面を入れ子にしない

- 自分で面を描く部品（Table・Stat・Accordion・`.filter-bar` 等）をCardで包まない。
- カードの中を分けたいときは、区切り線と小見出しで分ける。カードの中にカードや枠つきの部品を置かない。

### 3. 強調の予算を1画面に1つとする

- 1画面で最も強く見せるもの（主指標、主となる一覧・本文）を1つに絞る。強調は **大きさと位置** で示し、枠の色・影・背景色では示さない。
- 補助の値は小さく並べ、値が0のものや参考値は注記へ下げる。
- 色は意味を持つところにだけ使う（状態、強調する1つ）。すべての棒やラベルに同じアクセント色を塗らない。

### 4. 情報量に合った器を使う

- 1行しかない表や、100%になる割合は文章にする。
- 注記は、それが説明する節の見出しの近くに置く。面の外に浮かせない。

### 5. このrepositoryが提供するもの

禁止を書くだけでは選ばれる道具が変わらないため、地の上でまとまりを作る部品を足す。名前やpropsは実装PRで決める。

- **Section**（React部品 + テンプレート用クラス。ADR-0007により1:1）: 見出し・説明・操作・区切り線を持ち、面を持たない。
- **Stat** に、主指標用の大きい表示と、枠を持たず区切り線で並べる表示を足す。
- **Table** に、枠を持たず地の上に置く表示を足す。
- **Templates**: 「詳細画面」「標準アプリ」をこの階層に合わせて直し、集計・分析画面の見本を1つ足す。
- **文書**: DESIGN.md・design-system/README.md・screen-layouts.md に判断基準を書き、「Grid / Card 構成」を自由項目から外す。

### 6. 含めないもの

- **Cardの影・角丸・余白の値は変えない。** まず配置のルールで解決し、それでも面が強すぎる場合に別途判断する。
- **カードの装飾を増やす変更は保留する。** `.design-sync/templates/card-patterns/Card-titleRule-handoff.md`（タイトル罫線・accent色・フッター帯）は、カードで意味や強調を示す方向でこのADRと合わないため、実装しない。必要になったら、この階層の中で何を解決するかを示して改めて判断する。
- **Cardの枚数を機械的に制限しない。** 枚数では「もの」かどうかを判断できない。

## 理由

- 面が増えると、すべての面が同じ重さで見え、重要度の差が消える。差を付けようとして枠の色や影を足すと、さらに面が強くなる。面を減らし、強調を大きさと位置へ移すほうが階層が伝わる。
- Cardを薄くする（枠や影を消す）だけでは、箱の数は変わらず境界が曖昧になるだけで、どれが主役かは伝わらない。
- 判断基準を「名前を付けて単独で取り出せるか」にしたのは、人とAI agentが画面ごとに同じ答えを出せるようにするため。枚数や見た目の基準では画面ごとに解釈が割れる。

### 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| Cardの見た目を薄くする | 箱の数が減らない。境界が曖昧になるだけで強調の問題は残る |
| Cardを公開しない | 一覧の各項目や選択肢など、本当に「もの」を並べる画面で困る。shadcn/uiのre-exportを外す理由にもならない |
| lintでCardの枚数を制限する | 枚数では正しさを判断できない。正当な一覧画面が引っかかる |

## 結果

- まとまりの既定が「Card」から「見出しと余白」に変わる。新しい画面は地の上に節を並べ、カードは「もの」を並べるときだけ使う。
- 追加する部品・表示はすべて追加なので、既存の利用側は壊れない（MINOR）。既存画面の作り直しは各Applicationが自分の順番で行う。
- 「詳細画面」の見本はCard構成から節の構成に変わる。この見本をコピーしていたApplicationは、次に手を入れるときに合わせる。
- AI agentが参照する文書（DESIGN.md・design-system/）に判断基準が入るため、生成される画面のカードも減る見込み。

## 実装フェーズ

1. このADRと、DESIGN.md・design-system/README.md・screen-layouts.md の判断基準
2. Section の追加、Stat / Table の表示の追加
3. Templates（詳細画面・標準アプリの見直し、集計・分析画面の追加）
4. 利用側への適用（最初は dx-portal の周知リンク解析画面）

## 見直し

- フェーズ4を終えても面が強すぎると感じる場合は、Cardの影・角丸（§6）を見直す。
- 集計・分析画面の見本が2つ目のApplicationでも使われたら、Patternへの昇格を検討する。
